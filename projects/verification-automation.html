Overview

During my summer internship at Synopsys I created, from scratch, a set of Python scripts that automate the verification of LVS (layout versus schematic) results across all the cells of a project. An engineer runs the script and immediately knows which cells did not pass the LVS check, instead of having to review each cell individually.

Problem Statement

A project contains many cells, and each one has its own LVS result. Checking that status cell by cell is repetitive work, and it makes it easy to lose track of which cells still need attention. The team needed one place that answers a simple question reliably: which cells failed LVS.

No automation for this existed when I started, so the task began from nothing and had to be useful to engineers who would run it without knowing how it works inside.

Technical Challenges

  • Finding out where and how all the LVS data was exported, since the results had to be located and understood before anything could be automated.
  • Working in a Linux environment, which meant writing Bash scripts to move through the project and drive the flow.
  • Working with Tcl scripts, which I had to learn and use alongside Python and Bash.
  • Building everything from scratch with no template to follow, so design decisions about structure and output were mine to make.
  • Writing something other people could take over, because the work was done during a short internship and would continue after I left.

The Solution

I wrote Python scripts that collect the LVS results for every cell in a project and report which cells did not pass. Bash and Tcl scripts connect that logic to the Linux environment and the exported data. The result is a single command whose output tells the engineer exactly where to look.

Making it maintainable

  • All the code was uploaded to GitHub, so changes are tracked and the history is available to whoever continues the work.
  • Everything was documented in Jira, including how the data was exported and how the scripts work, because the project started from scratch and needed a clear starting point for future contributors.

Key Takeaways

  • Tools that start from zero depend on understanding the data first: tracing where results are exported and in what form came before any scripting.
  • Combining Python, Bash and Tcl in one workflow taught me to choose each language for the part of the job it handles best.
  • Version control and written documentation are part of the deliverable, not an extra, especially when someone else will inherit the work.
  • As an intern's first version, it still had plenty of room to improve, and the documentation was written so that others could build on it.
